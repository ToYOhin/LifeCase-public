# Data Model

## Conventions

- IDs are sortable opaque strings generated by application code.
- Timestamps are UTC ISO 8601 with microseconds; user timezone is stored separately where needed.
- Money is `amount_minor INTEGER` plus ISO currency code.
- JSON fields are validated at the service boundary and versioned when exported.
- Foreign keys are enabled for every SQLite connection.
- Originals are immutable; corrections append history rather than overwrite evidence.

## Core tables

### case_record

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | opaque case ID |
| type | TEXT | business Case type: `warranty`, `return_refund`, `reimbursement`, or `subscription_cancellation` |
| template_id | TEXT | actual reviewed template identity from the closed registry |
| template_version | INTEGER | version used for evaluation |
| title | TEXT | user-visible title |
| goal | TEXT | explicit desired outcome |
| status | TEXT | validated state-machine value |
| priority | INTEGER | user or policy ranking |
| version | INTEGER | optimistic concurrency for the Case lifecycle |
| created_at | TEXT | UTC |
| updated_at | TEXT | UTC |
| closed_at | TEXT NULL | UTC |

`status` is the typed Case lifecycle. Allowed transitions are:

- `intake` to `needs_review`, `ready`, or `abandoned`;
- `needs_review` to `intake`, `ready`, or `abandoned`;
- `ready` to `needs_review`, `in_progress`, or `abandoned`;
- `in_progress` to `needs_review`, `waiting_external`, `blocked`, `resolved`, or `abandoned`;
- `waiting_external` to `in_progress`, `blocked`, `resolved`, or `abandoned`;
- `blocked` to `needs_review`, `in_progress`, `waiting_external`, or `abandoned`;
- `resolved` and `abandoned` to `archived` only;
- `archived` has no outgoing transition.

Every successful transition increments `version` by exactly one. Entering `resolved` or `abandoned` sets `closed_at`; archiving preserves the original closure time. No other service may update Case lifecycle fields directly.

Migration 6 adds `template_id` and deterministically backfills existing `warranty` version 1 Cases to `warranty_claim`. Later reviewed-template slices add no migration: the typed built-in registry recognizes `warranty -> warranty_claim@1`, `return_refund -> return_refund_claim@1`, `reimbursement -> expense_reimbursement@1`, and `subscription_cancellation -> subscription_cancellation_claim@1`. Case reads and template evaluation reject an unknown type, ID, version, or mismatched combination. Existing `type` values are not silently renamed or migrated.

### Built-in Case template

Each versioned YAML is validated configuration, not authoritative Case or Claim storage. Its immutable typed projection contains:

- template ID, positive version, title, and ordered goal options;
- ordered required Claim fields and named conditional Claim fields;
- ordered evidence requirement keys with descriptions;
- alternative close-condition identifiers and forbidden-action identifiers;
- SHA-256 of the exact template bytes.

All identifiers use lower snake case and are at most 64 characters. Lists are bounded, non-empty, duplicate-free, and order-preserving. The template is loaded only through the closed built-in registry; arbitrary paths, URLs, YAML tags, anchors, aliases, expressions, and executable content are unsupported.

Missing-field evaluation is a read-only projection over authoritative same-Case Claims and reconstructs each canonical Claim value from its persisted JSON and hashes before use. Only a `confirmed` or `corrected` Claim with `contradiction = 0` satisfies its field. `candidate`, `inferred`, `rejected`, contradictory, missing, cross-Case, hash-invalid, or confidence-only Claims do not satisfy it. A conditional Claim is considered only when its exact named condition is supplied. Close conditions are alternatives: one recognized completed outcome sets `can_close`, but the evaluation does not change `case_record.status`.

### case_transition

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | opaque transition ID |
| case_id | TEXT FK | owning Case; cascades with Case deletion |
| prior_status | TEXT | validated state before the transition |
| new_status | TEXT | validated state after the transition |
| prior_version | INTEGER | expected committed Case version |
| new_version | INTEGER | exactly `prior_version + 1` |
| actor | TEXT | trimmed actor label, 1–120 characters |
| reason | TEXT | trimmed transition reason, 1–1000 characters |
| transitioned_at | TEXT | UTC commit time |

`UNIQUE(case_id, new_version)` makes one append-only history row correspond to one committed Case version. History is read by `new_version, id`; service code never updates or deletes individual history rows. The Case update and history insert share one `BEGIN IMMEDIATE` transaction. Migration 4 deterministically fills a missing `closed_at` from `updated_at` for any legacy row already in `resolved`, `abandoned`, or `archived` state before creating the history table.

### warranty_preparation_intent

Migration 17 adds one optional current-text row per Case for the Chinese warranty preparation
sheet's explicitly saved **本人诉求**. This is user draft content, separate from the Case goal,
Claim authority, Action definitions and approvals.

| Column | Type | Notes |
|---|---|---|
| case_id | TEXT PK/FK, NOT NULL | owning Case; cascades with Case deletion; service permits only `warranty` Cases |
| intent | TEXT, NOT NULL | at most 2,000 Unicode code points; verbatim text including whitespace, line breaks and emoji; NUL and unpaired surrogates rejected |
| version | INTEGER, NOT NULL | positive, independent optimistic version; increments on each successful explicit save |
| updated_at | TEXT, NOT NULL | UTC commit time, microsecond precision with `Z` suffix |

A missing row is read as empty text, version `0` and `updated_at=null`; GET never creates it.
PUT checks the independent expected version and saves in one `BEGIN IMMEDIATE` transaction.
The first save creates version `1`. Saving empty text clears the content while retaining the
row and increasing version; stale version-0 requests cannot recreate a cleared draft. Reads
validate stored text, version and timestamp; corrupt data is not silently replaced or used.

Saving intent does not increment `case_record.version`, alter Case timestamps/status/goal, or
append a `case_transition`. The lifecycle version-to-transition invariant above remains exact.
It also does not alter Claim/Action versions, actor/reason audit metadata, approvals, Source
records or Timeline events. Only the latest user text is retained: there is no edit-history
table, generic draft envelope, rendered preparation sheet or persisted fact snapshot. Current
facts and citations continue to be re-read independently when constructing the sheet.

The migration is append-only; migrations 1–16 and existing records are unchanged. Existing
databases use the verified pre-migration Backup gate. Whole-database SQLite backups naturally
retain this table, including cleared rows and their versions; no extra data-root file or
Artifact is created. Restoring a supported older backup migrates forward and leaves intent
unsaved, while restoring a new backup preserves its saved text/version and checks the new
service's reads. Builds whose migration catalog ends before 17 cannot open or restore this
new schema; downgrading a new database or backup to those builds is not supported.

### source_segment

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | stable segment ID |
| source_id | TEXT FK | parent source |
| sequence | INTEGER | stable ordering |
| page | INTEGER NULL | one-based document page |
| bbox_json | TEXT NULL | source coordinate box |
| text | TEXT | extracted content |
| extraction_method | TEXT | direct, email, OCR, manual |
| confidence | REAL NULL | extractor confidence |
| text_sha256 | TEXT | detects silent mutation |
| extractor_version | TEXT | versioned deterministic parser/segmentation contract |

For a Source, M1-03 computes stable IDs from the Source ID, extractor version, sequence, page, and text hash. A successful rerun deletes and reinserts that Source's complete segment batch inside one `BEGIN IMMEDIATE` transaction. The same object and extractor version therefore reproduce the same IDs, order, text, and hashes without duplicates. Empty or whitespace-only text is an explicit `EMPTY_CONTENT` failure and creates no segments.

### claim

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | claim ID |
| case_id | TEXT FK | owning case |
| field | TEXT | lowercase template field key, 1–64 characters |
| value_json | TEXT | canonical bounded JSON value |
| value_sha256 | TEXT | exact canonical value identity |
| comparison_sha256 | TEXT | normalized value identity for contradiction comparison |
| status | TEXT | candidate, inferred, confirmed, corrected, rejected |
| confidence | REAL NULL | Agent confidence, not truth probability |
| created_by | TEXT | user, rule, or agent origin |
| contradiction | INTEGER | derived Boolean for disagreeing active candidates |
| version | INTEGER | optimistic concurrency for Claim writes |
| created_at | TEXT | UTC |
| updated_at | TEXT | UTC |

Only `candidate` and `inferred` are active candidate states. Confirmation moves either state to `confirmed`. Correction can move candidate, inferred, confirmed, or corrected values to `corrected`; rejection can move the same states to `rejected`. Repeated confirmation/rejection and every mutation from rejected are forbidden. Every successful mutation increments Claim version exactly once and appends one event.

Claim values accept bounded strings, safe integers, Booleans, non-empty arrays, and string-keyed objects. Null, binary floating point, empty values, excessive depth/size, and non-canonical persisted values fail validation. Exact value hashes bind history/confirmation; case-folded Unicode/whitespace-normalized comparison hashes make contradiction recalculation deterministic.

For one Case and field, all active candidates have `contradiction=1` exactly when their distinct `comparison_sha256` count exceeds one. Confirmed, corrected, and rejected Claims are not active candidates and always have `contradiction=0`. The flag is recomputed in the same write transaction and is not separate evidence.

### claim_source

| Column | Type | Notes |
|---|---|---|
| claim_id | TEXT FK | composite PK |
| source_id | TEXT | authoritative Source identity |
| segment_id | TEXT | authoritative SourceSegment identity; composite PK member |
| segment_text_sha256 | TEXT | expected authoritative segment identity |
| quote_start | INTEGER | zero-based character offset; composite PK member |
| quote_end | INTEGER | exclusive character offset; composite PK member |
| quote_hash | TEXT | SHA-256 of the authoritative segment slice |
| relation | TEXT | supports, contradicts, context |
| attached_by | TEXT | bounded actor label |
| attached_at | TEXT | UTC |

ClaimSource stores no copied quote text. On both write and read, the Claim service joins Claim → Source → SourceSegment, requires equal Case ownership, recomputes the authoritative segment text hash, slices the authoritative text by the stored offsets, and recomputes `quote_hash`. Missing, stale, cross-Case, or tampered references fail closed.

The Source/Segment identity columns intentionally do not cascade through a database foreign key. M1 extraction replaces a Source's whole segment batch by delete/reinsert; a stable replacement must preserve Claim provenance, while changed or missing authoritative IDs remain as auditable stale references that service validation rejects. `claim_id` remains a cascading foreign key, so deleting the owning Case/Claim removes its joins.

### deadline

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | deadline ID |
| case_id | TEXT FK | owning Case; all service reads/writes require it |
| kind | TEXT | explicit, calculated, suggested |
| date_kind | TEXT | `utc_instant` or `local_date` |
| due_value | TEXT | canonical `...Z` UTC instant or `YYYY-MM-DD` local date |
| timezone | TEXT | validated IANA timezone, always present |
| status | TEXT | proposed, confirmed, passed, completed, dismissed |
| uncertainty | TEXT | evidence-backed, deterministic-rule, or personal-preference display contract |
| confidence | REAL NULL | copied from the explicit basis Claim only; not truth probability |
| rule_id / rule_version | TEXT / INTEGER NULL | required only for calculated dates |
| rule_parameters_json | TEXT NULL | canonical bounded parameters for the registered rule |
| rule_parameters_sha256 | TEXT NULL | exact parameter identity |
| version | INTEGER | optimistic concurrency; increments exactly once per command |
| definition_sha256 | TEXT | canonical kind/date/timezone/rule/basis identity |
| created_at / updated_at | TEXT | UTC audit timestamps; never calculation inputs |

`explicit` has exactly one current same-Case basis Claim and no rule. `calculated` has one or more ordered authoritative basis Claims and a closed registered rule; the current `calendar_days_after_basis@1` rule accepts exactly one basis and a bounded positive `days` parameter. `suggested` has no basis or rule and is always a personal follow-up preference. These shape rules are enforced by service validation and database checks.

UTC instants are timezone-bearing inputs normalized to microsecond `Z` form. Timezone-naive instants are invalid. Local dates have no implicit time-of-day. Explicit local wall-time conversion rejects nonexistent DST times and requires an explicit fold for overlaps. The IANA zone database is provided by pinned `tzdata` when the host, including Windows, has no system zoneinfo database.

### action

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | action ID |
| case_id | TEXT FK | owning case |
| kind | TEXT | collect_evidence, prepare_communication, follow_up, record_outcome |
| status | TEXT | proposed, blocked, ready, running, done, failed, cancelled in M5-02; approved is added only by M5-03 |
| risk_level | TEXT | A, B, C, D |
| payload_json / payload_sha256 | TEXT | bounded canonical kind-specific data and exact approval binding |
| blockers_json / blockers_sha256 | TEXT | canonical auditable blocker-code snapshot |
| version | INTEGER | optimistic aggregate version |
| created_at / updated_at | TEXT | UTC commit timestamps |

`action_requirement_claim` stores ordered Claim ID/version/value-hash/field bindings. Non-collection Actions bind available required template Claim fields with same-Case confirmed/corrected, non-contradictory authority; missing required fields keep the Action blocked. Analysis drafts select one deterministic representative per field when several usable Claims carry the same value, while retaining all facts in the Run binding. `collect_evidence` instead names one currently missing Claim or evidence requirement in its bounded payload.

`action_dependency` stores `(action_id, case_id, position, depends_on_action_id)` with composite same-Case foreign keys. Self edges, duplicates, and any cycle are rejected before write; reads recompute the complete graph and return a stable topological order using creation time and Action ID as ties. A dependency blocks until `done`.

`action_deadline` is an optional one-to-one binding containing Deadline ID, Case ID, Deadline version, and definition SHA-256. It never copies a UTC `due_at`. Reads return the freshly validated Deadline UTC-instant or local-date value with its IANA timezone, and any changed/missing/cross-Case binding fails closed.

`action_completion_evidence` stores ordered same-Case Claim, Source, or Artifact references. Claim references bind version and value hash; Source/Artifact references bind their persisted content SHA-256. At least one freshly validated reference is required by the `done` command.

`action_event` is immutable and stores event type, prior/new status and version, payload hash, blocker hash, actor, reason, and UTC occurrence time. `UNIQUE(action_id, new_version)` requires contiguous history ending at the current Action. Creation/revision/revalidation/status changes commit the aggregate, all owned joins, and one event in a single immediate transaction.

The original `prepare_communication` payload retains its two-key intent/recipient-role contract and deterministic Claim projection. The question-analysis draft variant additionally stores `draft_text`, `analysis_run_id`, `analysis_basis_sha256`, and `analysis_answer_sha256` in the existing canonical payload. The body is at most 500 Unicode code points; the complete payload retains the existing 2048 UTF-8 byte limit. This requires no table, migration, or copied fact/source store.

An analysis draft is a Risk-B Action explicitly saved by a user, not a fact, approval, or sent communication. Its exact text participates in the existing payload hash and Action version/event contract. The same Case/Run can have one such Action: exact initial-save replays recover it; conflicting text requires an explicit revision against its Action ID/version. Saving rechecks the Run and current facts/materials inside the same immediate transaction as the Action and event write.

For this variant, historical requirement bindings are checked against the immutable question Run's fact snapshot. Reads preserve the saved body and expose `analysis_basis_status` (`current`, `changed`, or `unavailable`); legacy Actions retain their original requirement-read rules. Changed or unreadable analysis authority cannot authorize saving, approval, or progression. Cancellation remains possible. The independent preparation-intent text is not automatically consumed or promoted to a Claim.

### action_progress

Migration 19 adds this single append-only table for manual progress/result notes on
analysis-bound repair-preparation Actions. The existing `action_event` cannot store
these notes without fabricating a transition or advancing the exact version used
by Approval. No old table or history is rewritten.

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | immutable manual record identity |
| action_id / case_id | TEXT FK | composite same-Case Action identity |
| position | INTEGER | consecutive append position, unique per Action |
| action_version | INTEGER FK | observed committed `action_event(action_id, new_version)` |
| kind | TEXT | progress or result, never an Action status |
| text | TEXT | original human text, at most 2000 code points / 8000 UTF-8 bytes |
| actor / reason | TEXT | bounded audit metadata; actor is a local label |
| created_at | TEXT | UTC commit time |

Append rechecks Action version, current analysis basis, and the expected last record
inside one immediate transaction. It does not update Action/Case versions or
statuses, facts, payloads or approvals. Record IDs cannot serve as Claim, Source or
Artifact completion evidence. Timeline projects references with manual-origin
semantics and omits the note body. Whole-database backups retain these rows under
the existing backup contract.

For completed analysis-bound Actions, retained Claim completion references are
validated against their immutable historical authority, not silently replaced by
the current corrected value. Current complete commands retain their strict current
Claim/version/hash checks. A subsequent basis change is visible through the existing
`analysis_basis_status`; historical completion is not replayed or rewritten.

The Deadline tables above are implemented by migration 8. Migration 9 adds the Action aggregate; migration 10 safely rebuilds the Action status constraint and adds Approval authority plus the approved Action state. No Action/Approval migration is shared with M6.

### agent_run and agent_stage_run

Migration 18 adds only nullable `agent_run.input_binding_json` and
`input_binding_sha256`. They are paired for `portfolio-live-q1-` question Runs;
old Run rows remain NULL and are not backfilled. The canonical binding is bounded
to 100,000 UTF-8 bytes and stores the original question, separate retrieval expression,
Case-scoped current-fact values/versions/audit/quoted excerpts, material and Segment
identities/hashes, basis hash and authorization hash. It stores neither complete
material text nor Provider output/credentials. This is necessary because the earlier
input hash alone cannot reconstruct the question or its authorized facts on restart.
Stored bindings are immutable history; current-facts remains authoritative.

Read and Backup/Restore validate binding shape, hashes and Case, not whether its
basis remains current. Execution/repair/finalization compare current authority in
their existing transactions. Old schema backups without these columns remain
readable; builds without migration 18 cannot open or restore the new schema. No new
table, dependency or generic workflow/version framework is introduced. The earlier
statement below excluding raw input bodies remains true: the new fields are a
bounded, specifically validated question/authority contract.

Migration 7 creates the provider-neutral M3-02 orchestration authority. Migration 16 removes the `agent_run.case_id` uniqueness so Live Agent can preserve terminal Run history; the `(id, case_id)` key and every stage composite foreign key remain Case-scoped. StageRunner still enforces one Run by default, and only an explicit history command may create another ID. Each Run has a durable optimistic version, current/last-completed stage, queued/running/checkpointed/needs-review/cancelled/completed status, cancellation flag, timestamps, and maximum/used/reserved call, input-token, output-token, total-token, and CNY minor-unit counters. The default typed budget permits at most 14 calls and CNY 100 minor units (CNY 1); database checks prevent used plus reserved amounts from exceeding configured ceilings.

`agent_stage_run` has one row per `(run_id, stage)` and repeats the Case ID under a composite foreign key to prevent cross-Case association. It records fixed stage/input/output/checkpoint schema versions, the canonical input-scope SHA-256, optimistic version, status, a maximum of two calls, per-stage maximum/used/reserved budgets, repair count, provider/model metadata, aggregate latency, bounded canonical checkpoint JSON and its SHA-256, stable error/retryability data, and timestamps. Fixed stage and status sets are database constraints.

Migration 11 extends only the closed provider identity constraint with `ollama`. Migrations 12, 13 and 14 perform the same shape-preserving rebuild to admit `groq`, `mistral` and `deepseek`, retain existing rows, and continue rejecting unknown provider identities. None changes checkpoint, Claim, Case, Deadline, Action, Approval, budget, or recovery authority.

The call count and token/cost reservation commit before provider execution. Finalization transactionally moves actual validated usage into used counters and clears the reservation; when cost is unavailable, the reserved CNY amount is charged. Explicit interrupted-run recovery charges the remaining reservation conservatively and moves both run and stage to `needs_review`. Only a completely validated checkpoint is stored. Raw input/prompt bodies, complete evidence, provider response/SDK objects, credentials, SQL, paths, and remote error text are not columns or persistence inputs.

M3-03 requires no new migration. Its versioned warranty extraction checkpoint is stored in the existing bounded `agent_stage_run.checkpoint_json`. The checkpoint uses `extracted`, `inferred`, and `unknown` only as extraction-origin semantics. `extracted` maps to an existing `candidate` Claim with `created_by=agent`; `inferred` maps to the existing inferred Claim state; unknown creates no Claim. Citation authority remains in Source/SourceSegment and ClaimSource, not in checkpoint text.

When an M3-03 extract stage succeeds, Claim/ClaimSource/created-event rows, deterministic contradiction recalculation, stage usage, and checkpoint state commit in one transaction. The transaction-aware ClaimService entry point accepts only validated `CreateClaimCommand` values and still reuses all M2-02 Case/hash/excerpt validation. A failure rolls back every business and Agent row in that finalization attempt.

### decision

Records the facts available at decision time, rule/template versions, recommendation, user response, and eventual outcome. This supports Decision Replay without trusting mutable conversation history.

### artifact

| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | artifact ID |
| case_id | TEXT FK | owning case; cascades on case deletion |
| source_id | TEXT FK NULL | originating source; set null if source metadata is deleted |
| type | TEXT | source, derived text, thumbnail, draft, calendar, pack, manifest, or backup |
| relative_path | TEXT | data-root-relative path; never a machine-specific absolute path |
| sha256 | TEXT | content digest |
| size_bytes | INTEGER | non-negative validated byte count |
| created_by_run | TEXT NULL | future Agent run ID; no FK until that table exists |
| created_at | TEXT | UTC |

An original-source import creates one `artifact` row with `type=source`, linked to its Source row. Repeated explicit imports therefore create separate Source and Artifact records that reference the same object path.

M6-01 retains each Evidence Pack as an existing `artifact` row with `type=pack`, no `source_id`, and a content-addressed relative export path. No new table or migration is required. The ZIP has independent integer `format_version=1`, a minimum application version, and four visible layers: `original`, `derived`, `generated`, and `confirmed`. Its manifest binds each member path to authority type/ID/version, media type, size, and SHA-256; `checksums.sha256` covers all data members plus the manifest. Previous pack/manifest/backup Artifacts are deliberately excluded so repeated export is deterministic and non-recursive.

M6-02 Backup is a filesystem-retained whole-authority contract, not an `artifact` row and not Case-scoped export metadata. Backup format 1 contains one SQLite online snapshot and exactly the files referenced by snapshot `source.object_path` or `artifact.relative_path`. The canonical manifest records all-Case scope, sorted Case IDs, database and member relative paths, authority type/ID/Case bindings, byte sizes, SHA-256, the applied migration name/checksum prefix, and minimum application version. Backup identity is the final archive SHA-256. A restore validation ticket uses that same opaque hash and is always revalidated before apply; no database table is trusted as a restore approval. M6-02 adds no schema migration.

The Artifact row is download authority, not the browser's cached response. Reads rejoin the Case-scoped row to a safe relative path, verify stored size/hash, and then verify archive paths, manifest membership, size declarations, and checksums. A changed byte, missing member, duplicate/case-fold-colliding path, traversal/absolute path, stale source file, or over-limit member fails closed.

## Search

### source_segment_fts

`source_segment_fts` is a regular SQLite FTS5 virtual table and a disposable projection, never authoritative storage. It contains:

| Column | Indexing | Notes |
|---|---|---|
| `source_id` | UNINDEXED | copied only for transactional per-Source replacement and validation |
| `segment_id` | UNINDEXED | stable SourceSegment citation ID |
| `text` | trigram | searchable copy of authoritative `source_segment.text` |
| `text_sha256` | UNINDEXED | copied integrity value, checked against the authoritative row |

The FTS rowid equals the authoritative `source_segment.rowid`. Every query joins `source_segment_fts` to `source_segment` and `source`, applies `source.case_id = ?` in SQL, returns text and citation fields from the authoritative rows, and recomputes the authoritative text hash before returning a hit.

Migration 3 creates the trigram projection and backfills existing segments inside the migration transaction. A successful SourceSegment batch replacement deletes the old Source projection, replaces the authoritative rows, inserts the new projection, and records extraction state inside one `BEGIN IMMEDIATE` transaction. Any failure rolls back all four effects.

The complete projection can be dropped and rebuilt transactionally from `source_segment` alone. Rebuild performs the FTS5 integrity command, exact count/content/identifier comparison, and authoritative text-hash validation before commit. Vector search is not a default dependency. Later claim/title/communication projections require their owning milestone and privacy review.

## Evidence Context (ephemeral projection)

Evidence Context is an immutable in-memory projection and creates no table. Its request contains:

- explicit `case_id`, FTS query, and result limit;
- adjacent-before and adjacent-after counts, each from 0 through 5;
- an explicit allowlist of authoritative Source trust labels;
- total and per-item UTF-8 text-byte ceilings.

The current authoritative Source schema supports only `untrusted`. An allowlist containing that typed label admits imported evidence; an empty allowlist deterministically rejects every hit. This trust label describes imported content as untrusted data rather than instructions. ClaimSource `relation` and warranty-template evidence requirements retain their M2-02/M2-03 meanings and are not silently reinterpreted as M2-04 retrieval eligibility.

The output contains ranked initial matches and budget-admitted Context items. A citation contains `case_id`, `source_id`, `segment_id`, `sequence`, `page`, and `text_sha256`. A match also contains its one-based production retrieval rank and BM25 score. An item contains the complete authoritative text, exact UTF-8 byte count, `match` or `adjacent` origin, and all selecting match ranks in ascending order.

Initial matches preserve M1-05 order. Same-Source windows are merged when they overlap or touch, ordered by earliest selecting rank then Source ID/sequence, and deduplicated by Segment ID. Budget admission follows that deterministic order. A Segment exceeding the per-item ceiling or remaining total ceiling is omitted whole and sets `truncated`; no partial text or half citation is produced. Total bytes cannot exceed 100,000 and one item cannot exceed 32,000 bytes.

All Context construction occurs in a stable SQLite read transaction. Initial and expanded citations rejoin authoritative Source/SourceSegment rows with `source.case_id = ?` in SQL and recompute text hashes. Source sequences must be zero-based and continuous. Context is disposable and can always be regenerated; it never becomes evidence authority and never mutates Case, Claim, SourceSegment, FTS, or template state.

### Evidence-backed answer checkpoint

M3-04 introduces no table or migration. The existing `agent_stage_run.checkpoint_json` stores a bounded `validate.rag.checkpoint.v1` value only after citation validation. Its payload is `evidence_backed_answer.v1` with `answered` or `unknown` status, ordered answer statements, exact quote references, an uncertainty reason for `unknown`, and the fixed tool name/call count/Context SHA-256.

Each answer quote reference contains `case_id`, `source_id`, `segment_id`, `sequence`, `page`, authoritative `text_sha256`, quote offsets, and `quote_hash`. Source text and the complete Evidence Context remain ephemeral stage input and are not copied into the checkpoint. The checkpoint is a validated result, not evidence authority; validation and finalization rejoin Source/SourceSegment under the same Case and recompute hashes.

## Case workbench (ephemeral projection)

M4-01 adds no table or migration. `CaseWorkbenchItem` combines one authoritative `case_record` with an `is_today` classification, ordered M2-03 missing Claim/evidence identifiers, and the latest admitted authoritative activity timestamp/kind. It does not copy Claim values, Source text, Agent checkpoints, or object paths.

Today is the set of `intake`, `needs_review`, `ready`, `in_progress`, `waiting_external`, and `blocked` Cases. `resolved`, `abandoned`, and `archived` remain readable in the full list. Latest activity is selected deterministically from admitted authority timestamps; equal timestamps use a fixed kind rank and stable activity ID. List ordering is Today first, priority descending, activity time descending, then Case ID ascending. M5-02 supplies a bounded authoritative next Action or `null`. Deadline records remain separately available, while summary deadline risk remains uncalculated until a reviewed risk policy exists.

## Evidence review (ephemeral projection)

M4-02 adds no table or migration. `EvidenceReviewResult` contains one Case ID and ordered `EvidenceReviewItem` values for active candidate/inferred Claims. Each item holds the authoritative Claim, zero or more current `ReviewCitation` values, every same-field confirmed/corrected Claim, and an `is_next` marker.

A review citation combines ClaimSource audit metadata with a fresh authoritative same-Case Source/SourceSegment join: source display name, Segment identity/order/page, complete Segment text/hash, exact quote bounds/hash/text, relation, attaching actor, and time. It is disposable UI data, not evidence authority. The projection never copies Source bytes or creates a second decision/history store.

Ordering is template field order, then lexicographic extension fields. Within one field, contradictions precede non-contradictions, inferred precedes candidate, and creation time plus Claim ID break ties. An empty queue has `next_claim_id = null`. Review decisions mutate only the existing M2-02 Claim aggregate through its optimistic transactional commands.

## Case Timeline (ephemeral projection)

M4-03 adds no table or migration. `TimelineResult` contains one Case ID, ordered immutable `TimelineEvent` references, and explicit availability for later approval/communication families. Event identity is the event kind plus the underlying authority ID; it is stable projection identity, not a new durable row.

Admitted authority types are `source`, `source_extraction`, `artifact`, `case_transition`, `claim_event`, `agent_run`, `agent_stage_run`, and immutable `deadline_event`. Safe events retain UTC time, authority/subject/parent IDs, persisted actor or origin, bounded label/status/prior-status/version/reason metadata. They omit Source and Claim value bodies, object/relative paths, prompts, complete checkpoints, credentials, SQL, and machine paths.

Ordering is timestamp ascending, closed kind rank, and authority ID. Case/Claim/Deadline/Action/Approval immutable versions must be contiguous and end at current authority; all basis, graph, payload, definition, and history references are revalidated inside one stable read transaction. Source extraction and Agent rows expose only their latest durable status snapshot because no append-only intermediate history exists. Approval availability is `available`; communication is explicitly an `available_as_action_projection` local draft, not an external-send record.

## Portable export

Portable IDs and relative paths must not encode a drive letter, user name, or machine-specific directory. Export schema contains `format_version` and the minimum application version needed for restore.

## M7 evaluation corpus (repository fixture authority)

M7-02 adds no database table or migration. `fixtures/synthetic-cases/m7-v1/` is immutable repository evaluation input, not user or Case authority. Its corpus manifest fixes the version, exact Case membership, and 8/8/7/4/3 distribution. Each Case directory contains one declared synthetic input, separate expected Claim/gap/Deadline/Action JSON documents, strict metadata, and one recorded observation document.

Every evaluation identifier is Case-scoped; citations bind Case/Source/Segment IDs, portable input path, segment SHA-256, quote offsets/hash, and relation. Expected and observed files remain separate, and the evaluator performs no write to SQLite. Canonical reports contain only opaque IDs, classifications, aggregate counts/hashes, limitations, and safe failure codes. The corpus hash is derived from sorted portable member paths and member SHA-256 values; it contains no absolute path or wall-clock timestamp.

## Migration policy

- migrations are immutable after merge;
- each migration has a test from a clean database;
- each applied migration stores its name, SHA-256 checksum, and UTC application time;
- one migration runs inside one `BEGIN IMMEDIATE` transaction and rolls back fully on error;
- the migration metadata table may remain after a failed first schema migration; rerunning is the supported forward-repair path;
- destructive schema changes require a backup and an ADR;
- data backfills are restartable and record progress;
- downgrade is optional only when a forward-repair path is documented and tested.
