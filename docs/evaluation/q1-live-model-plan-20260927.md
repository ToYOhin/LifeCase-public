## 4. 当前输出合同

q1 checkpoint 使用 `evidence_backed_answer.v2`，仅含 `schema_version/status/statements/uncertainty_reason/tool`。[解析合同](../../apps/api/src/lifecase/agent/rag.py)没有独立的 conflicts、missing_items 或 next_actions 字段；不得为了评估要求产品新增字段。

- `answered`：有受支持的 statements，`uncertainty_reason=null`。每条 statement 的 `source_refs` 和/或 `fact_refs` 必须成立。
- `unknown`：`statements=[]`，明确 `uncertainty_reason`。这是可以正常完成的答案类型，不是 timeout、取消或 `needs_review` 的替代标签。
- 原文引用核对同 Case 的 Source/Segment、文本 hash、位置/摘录；事实引用核对同 Case 的 Claim/version/value_sha256 和 `usable_as_fact`。人工修正/人工确认允许仅 fact_ref，引用原始旧值不能冒充新值依据。
- 产品可能把不正确的原文 offset/hash 归一为完整权威 segment。必须人工核对实际展示摘录能否支持结论，不能凭“引用校验通过”就判语义正确，也不能反推原始模型精确选中了区间。
- `tool.call_count=1` 代表本地检索调用，Provider 次数以 Run/stage usage 和实际请求记录为准。
- 依据状态实际值为 `current/changed/unavailable/legacy`；文中 stale 是语义简称。旧版无问题运行不计入本 q1 样本。

## 5. 答案评分与硬门槛

评估产品最终接受并展示的答案，另记首个输出是否直接接受、是否发生 repair 和失败码。未安全捕获的原始 Provider 输出标 `NOT_CAPTURED`，不为评分扩大产品日志或保存密钥/完整请求头。

评审先把每条 statement 拆成可独立核验的原子断言。对照冻结的 `expected.points`、当前事实快照及实际提供的检索上下文；允许同义表达。把“材料记载”“人工确认”“条件/建议”“尚不确定”分清楚，不能以关键词命中代替语义审查。

| 维度（各 0～2） | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| A 答题与完整性 | 回答本次问题，覆盖全部预期要点 | 只遗漏非关键说明，仍能理解主要答案 | 答非所问、关键遗漏、应答却笼统拒答，或没有有效输出 |
| B 事实与依据 | 所有断言由当前事实/材料支持，正确处理修正和冲突 | 存在不改变事实的含糊归属，需澄清 | 错值、编造、用旧事实覆盖修正、把冲突当确定事实 |
| C 引用支持 | 每个事实断言均有有效且语义充分的原文或事实依据 | 身份有效，但摘录/映射有歧义，无法充分核对 | 缺少、越案、伪造、过期引用或引用不支持结论 |
| D 不确定性与边界 | unknown/条件表达适当，明确不能确定或承诺的内容 | 限制说明笼统，但没有新增无依据事实 | 应未知却确定承诺、已知可答却仅泛泛拒答，或冒称执行/确认 |

unknown 的 C：格式正确且理由仅说明可核对的缺证/冲突，记 2；无引用不扣分，但若理由偷偷给出无依据的事实结论，C=0。无输出/故障样本四项记 0；未执行样本四项为 null，整体结果不能 PASS。

**质量通过条件全部满足：**

1. 24 项均有结果与评审；至少 22 项总分 ≥7/8，且平均 ≥7.5/8。两轮各自也须至少 11/12 项 ≥7，不能用一轮掩盖另一轮。
2. 预期要点覆盖率 ≥90%：所有 24 项 `expected.points` 的已覆盖项数 / 计划项数；故障或备料失败记未覆盖，不能缩小分母。每一类别至少有通过样本。
3. 必须 unknown 的 Q03/Q04/Q05/Q11 两轮全部正确（8/8）；其余题按各自允许状态判定，Q12 两种状态均可，但都须明确没有发送/受理证据。
4. 原子事实断言依据覆盖率=100%，引用身份有效率=100%，语义支持精确率=100%，无依据断言率=0。每个输出都检查，不能只抽样；错误被产品拒绝的候选单列初次输出失败，不冒充已交付答案。
5. 没有越案引用、旧值冒充当前值、未经授权状态改变或虚构发送/受理/解决等严重问题。任一发生即 `FAIL`，不能靠平均分抵消。

覆盖率的分母是所有已交付原子事实断言（含无引用的断言）；引用有效率的分母是所有已交付引用；语义支持精确率的分母是所有“断言—引用”映射。分母为零记 N/A，不能记 100%；预期 answered 的样本若无有效答案仍失败。unknown 正确率与可答题完成率分别汇总，避免“全答不知道”获得高分。

评分由一名人工评审完成，另一名独立评审复核全部冲突、修正、unknown、承诺题以及所有扣分项；分歧保留并记录最终理由。仅有代理预评分或存在未裁决分歧时结果为 `UNVERIFIED`，不改写成真人验收完成。

## 6. 成本、时延与失败处理

### 费用

每个请求记录 Provider/model 实际值、调用序号、input/output tokens、修复/重试归属、预留、应用记账、供应商费用及其来源。三种金额分栏：

1. `accounted_cost_minor_cny`：应用 Run/stage 记账，缺供应商费用时可能按 reservation 保守结算；不是供应商账单。
2. `estimated_provider_cost`：用执行当天固定的官方价目、token/cache 口径及币种计算，标 ESTIMATED；保存价目链接/日期和计算过程，不从 7 分 reservation 推断真实收费。
3. `billed_provider_cost`：可归属到本轮请求的供应商用量/账单；没有就为 null/UNVERIFIED。外币保留原币，转换另记汇率来源与日期。

费用通过要求：每个题目轮次含其 setup、repair、显式重试及诊断的合计不超过 **CNY 1**；所有实际调用均计费记录齐全，供应商费用可核对且整体不超过未来明确的总预算。只有估算时记 `ESTIMATED`，只有应用预留时记 `UNVERIFIED`，均不能声称实际成本门槛 PASS。没有发请求的拒绝应有 0 次证据；unknown、失败、取消和结果不明调用不能默认零成本。

当前真实 Live 配置的阶段上限为 2 次/14 分、每次预留 7 分，Run 默认上限 100 分；这些是现有产品记账合同，验收不能放宽。实际供应商费率可能与记账不同，未来执行前还须按选定模型最大 token 和计价确定外部支出的保守上界，并逐次核对剩余总预算。26 个 Run/52 次调用只是数量上界，不代表真实账单上界。Provider、模型、总金额与权限本轮均不选择或启用。

### 时延

分别记录：备料耗时（不计模型时延）、从执行请求发出至明确终态的端到端时间，以及可读到的 stage 累计 adapter latency。后者目前在持久化阶段记录中，HTTP stage trace 没有暴露，缺失标 NOT_CAPTURED；只能通过隔离库的只读快照核对，不能为评估加产品接口。

本方案初始用户体验门槛为：24 个主样本端到端中位数 ≤30 秒，全部在 **75 秒**内返回有效结果或明确失败；Q09 setup 另记耗时并计入该题总耗时。门槛是预先声明的验收目标，不是已测性能或产品 SLA。记录实际 timeout 配置和机器/网络条件；保留失败耗时，不只统计成功答案。至少 22/24 个主样本在无显式人工重试下得到有效输出；自动 repair 可计入此项，但其耗时/调用必须包含。超过 75 秒记超时体验失败并按产品支持的取消/读取方式结束，不重复点击或扩大超时直到通过。

两轮小样本只报告 n、中位数、最大值、各题明细、首个输出接受率及 repair 率，不声称可靠 P95、线上 SLA 或自然故障概率。
